# Test plan: Restful-Booker practice API

## 1. Purpose and scope

Check that the Restful-Booker booking API (https://restful-booker.herokuapp.com), a public API built for testing practice, behaves correctly and refuses bad input.

**In scope:** reading bookings, creating and searching bookings, input validation, response formats, and (when the demo login is supplied) authentication and changing or deleting bookings.
**Out of scope:** performance and load testing, security penetration testing, the web user interface.

## 2. Test approach

| Level | How |
|---|---|
| Functional API tests | One request per test case, with assertions on status code, response body, field types and headers |
| Negative tests | Invalid, missing, oversized and malformed input |
| Data consistency | A booking that is created can be read back and found by search with the same values |
| Exploratory | Free exploration of the endpoints in Postman before writing each case; findings become test cases |
| Regression | The cases that pass today run on every change in GitHub Actions |

Test cases are written as a Postman collection (generated by `scripts/build-collection.mjs`) and run with Newman. The list of all cases is in `docs/TEST-CASES.md`.

## 3. Test environment

- API: https://restful-booker.herokuapp.com (shared public service that resets its data every few minutes).
- Tools: Postman, Newman, Node.js, GitHub Actions.
- Test data: bookings are created with a unique first name (`Qa<timestamp>`) so tests never depend on other people's data.

## 4. Risks and limits

- The service is shared and public, so data can change or reset between two requests. Tests never rely on pre-existing data except to read one existing booking id.
- The service can be slow or briefly unavailable (it is free hosting); a failed run should be repeated before it is reported as a defect.
- Requests are kept small and few. The suite sends about 20 requests per run.

## 5. Entry and exit criteria

- **Entry:** the API answers `GET /ping`.
- **Exit:** all regression cases pass; every failing case in the "known defects" folder has a bug report in `docs/BUG-REPORTS.md`.

## 6. Deliverables

Test plan (this file), test cases, Postman collection and environment, Newman HTML reports, bug reports, and a GitHub Actions pipeline.
